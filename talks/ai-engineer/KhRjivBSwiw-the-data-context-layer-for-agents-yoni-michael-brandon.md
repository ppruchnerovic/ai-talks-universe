## Description

Two Rust types are both called PostingList, but changing them breaks different code. A text search finds both; a context graph preserves their identities and exposes their separate dependencies. Yoni Michael and Brandon Callender use that distinction to connect data engineering and coding agents. For a data system, valid SQL can still produce the wrong answer when a join multiplies rows or a refactor changes a metric's meaning. Michael describes a context layer that computes grain, lineage and relationships from transformation code, checks join assumptions against real data, and makes the resulting evidence queryable before an agent acts.

Callender builds a smaller version over selected crates in Qdrant. Tree sitter extracts syntax, Rustdoc resolves symbols, and Neo4j stores the relationships. An agent can then ask which symbols depend on a particular type instead of repeatedly searching files and inferring connections. The workshop's central complication comes next: given better graph tools, the agent may still choose grep. Tool naming, familiar output formats and prompting become part of the interface, and evaluations must measure whether the tools are actually used. Cached comparisons separate getting an answer right once from getting it right across repeated runs, while trace inspection catches flaws hidden by a favorable score. The closing discussion explores incremental indexing, Python's harder resolution problem, small auditable semantic operations with Fenic, and the work required to extend a classroom example into a maintained context layer.
