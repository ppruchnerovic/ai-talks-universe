## Description

Speculative decoding drops a demo model from roughly 58 tokens per second to 16 instead of speeding it up. Du'an Lightfoot and Khaja Omer use that failed optimization to make a practical point: a faster inference configuration has to be measured against the actual model, hardware and workload. Their workshop starts with the decision to use hosted APIs or run inference on dedicated GPUs, then gives participants a Kubernetes namespace containing a Jupyter notebook and a vLLM endpoint. Qwen provides the example model for exploring how an agent's prompts, responses and repeated tool calls consume latency and memory.

Lightfoot builds the foundation through streaming measurements, model configuration, memory budgets, prefill, decode and KV caching. The notebooks separate per request generation speed from aggregate throughput, examine cold and warm prefixes, and compare dense models with mixtures of experts. Omer then changes the serving deployment to an FP8 model, repeats the load tests and checks simple output quality cases before moving to speculative decoding. When the drafter makes performance worse, he examines acceptance rate, model compatibility and GPU contention, then returns to the baseline. The final tuning exercise finds the concurrency point where throughput flattens while latency rises, changes the sequence limit, and measures the result again. A notebook failure also changes the model used in the final comparison, which the presenters acknowledge. The reusable method is to establish a baseline, change a serving parameter, rerun realistic load tests and evaluate quality alongside speed.
