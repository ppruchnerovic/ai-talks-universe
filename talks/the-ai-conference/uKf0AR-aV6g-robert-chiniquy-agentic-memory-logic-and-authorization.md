# Robert Chiniquy: Agentic Memory, Logic, and Authorization

## Description

This talk introduces a specific, implementable architecture for context-aware agent authorization — using structured memory as a first-class input to the policy evaluation hot path. The core argument is that agent tool calls occupy a gap in the authorization model taxonomy. No single existing model handles them well: RBAC can confirm a user has a role that includes Jira access, but cannot scope a tool call to a specific project without creating a role per project. ABAC can evaluate request parameters against static constraints, but requires someone to have pre-configured those constraints — it doesn't know why project ALPHA is the right scope. ReBAC can traverse a relationship graph to determine that a user is related to project ALPHA through a team, but doesn't account for temporal context (the user was on ALPHA last quarter, now on BETA). The missing input is situational context: what is this user currently working on? What has their agent been doing in this session? What tools do people in this user's role typically use? The talk will present: A memory architecture designed for authorization — not general-purpose agent memory. Three typed stores (worker memory from identity/HR/project systems, agent session memory from conversation context, organizational baseline memory from usage analytics), each with different trust levels, update semantics, and confidence scoring. Temporal validity ranges on every fact for point-in-time audit queries. This draws on and synthesizes ideas from the academic agent memory literature (Zep/Graphiti for temporal knowledge graphs, Hindsight for belief evolution with confidence, MIRIX for typed multi-agent stores) but is purpose-built for the authorization use case. A write/read split architecture for the hot path. Memory facts are extracted asynchronously (tolerating LLM latency for fact extraction and confidence scoring). Authorization decisions are evaluated synchronously against pre-compiled facts using Datalog — deterministic, terminating, auditable, sub-millisecond. The evaluation does not call an LLM. It does not make network round-trips to external stores. The facts are local and pre-compiled. Memory-informed delegation policies. Concrete Datalog examples showing how a delegation can reference memory predicates instead of static parameter constraints. A rule that says "allow this Jira create_issue call if the target project is one the user is currently working on, per memory, with confidence above 0.7" — and if confidence is below the threshold, escalate to a human approval flow. Plus anomaly detection via organizational memory baselines: "this tool is not typical for this user's role" as a governance signal, not a hard deny. An honest treatment of the unsolved problems — particularly the local authentication and configuration barrier for non-technical users, and the challenge of governing memory itself (provenance, retention, review cycles) when memory facts influence authorization decisions.
